# Plan 5.12 — BOS 工具面扩展（master plan）

> **本文件是 master plan**，按 6 个能力切成 6 个 sub-plan。每个 sub-plan 自己的 doc 在 docs/plans/ 下平铺，命名 `2026-04-XX-plan-5.12.N-<topic>.md`。
>
> Sub-plan 在轮到它时再展开写——不一次写完，因为高复杂度的（业务规则 / 实体 / 转换）需要 Tier B 深度侦察的产出来定接口。
>
> **For agentic workers:** REQUIRED SUB-SKILL: `superpowers:subagent-driven-development` 给具体 sub-plan 任务。Sub-plan 用 checkbox（`- [ ]`）跟踪。

**Goal:** 在 v0.1 Alpha 之前，把 BOS 6 个高频客户场景（实施顾问 80% 的工作）封装成 agent 工具，让 OpenDeploy 真正能"AI 替顾问做实施"，而不只能加文本字段。

**Architecture:** 沿用 Plan 5.5 起的工具栈架构——`bos-write-tools.ts` 注册所有 `kingdee_*` 写工具；每个工具走 `bos-writer.ts` 做事务包装（含 backup）；XML 操作集中在 `bos-xml.ts`；SQL 走 `validator.ts`（Plan 6 加白名单）。新工具：6 大类 + 配套反查 + 业务规则的 IronPython validator。

**Tech Stack:** TypeScript + mssql + Vitest（沿用 Plan 5.x 栈，无新增）

**Scope 红线（本 plan 不做）：**
- 不做客户端 UI 化的"BOS Designer 替代"——所有交互走 chat
- 不做转换规则的**创建**（10 个 ConvertPolicy 子类太复杂）→ 仅做"读 + 解释"，留 v0.2 做创建
- 不做审批流 / 套打 / 报表 / 实时预警 / 消息中心 / 编码规则 / 过滤方案——按当前侦察留 v0.2-v0.3
- 不做字段 UI 布局的精细控制（Top/Left 仍默认左上角，agent 不暴露完整 LayoutInfo 模型）

## Sub-plan 范围概览

每个 sub-plan 的细节 plan doc 单独写。这里只给 scope summary + 估时 + Tier B 依赖。

### 5.12.1 字段类型扩展（独立，估 3-4 天）

**Tier B 侦察需求**：低（capability-catalog 已实证够用，最多再补每类 XML 节点形态半天）

**P0 字段类型清单**：

| 大类 | type 枚举 | C# 类 |
|---|---|---|
| 文本 | `text` | TextField |
| 大文本 | `large_text` | LargeRichTextField |
| 整数 | `int` | IntegerField |
| 小数 | `decimal` | DecimalField |
| 金额 | `amount` | AmountField |
| 数量 | `qty` | QtyField |
| 日期 | `date` | DateTimeField (date-only mode) |
| 日期时间 | `datetime` | DateTimeField |
| 复选框 | `checkbox` | （CheckBox flavor of TextField，待实证） |
| 单选下拉 | `combo` | ComboField |
| 多选下拉 | `mul_combo` | MulComboField |
| **基础资料** | `base_data` + `refBaseDataObjectKey` | BaseDataField（6 子类按 ref 类型分） |
| **基础资料属性** | `base_property` + `sourceField` + `srcDisplayFieldName` | BasePropertyField |
| **引用属性**（高级）| `reference_property` | ReferencePropertyField |
| 颜色 | `color` | ColorField |
| 手机号 | `mobile` | MobileField |

**新工具**：
- `kingdee_add_field` 扩参数（保持向后兼容，type 默认 text）
- `kingdee_describe_basedata(refBaseDataObjectKey)` — 反查某基础资料有哪些属性可带（base_property 的前置）
- `kingdee_get_extension_fields` 增强按 entity 分组（与 5.12.2 联动）

**测试**：每个 type 至少 1 单测 + base_property/reference_property 各 2 单测（含 sourceField 校验）

### 5.12.2 实体（1:N 子表）（依赖 5.12.1 完成，估 4-6 天）

**Tier B 侦察需求**：中-高 — 半天补 SQL 蓝图（CREATE TABLE 列模板 + tracker FTABLEID 选择 + OBJECTTYPEREF 行）+ 半天找一个真实 SAL_SaleOrder 的 entity XML 节点形态实证

**P0 工具**：

| 工具 | 范围 |
|---|---|
| `kingdee_list_entities(extensionFid)` | 列父扩展所有 entity（head + 多个 entry + 嵌套 sub-entry），含 TableName / EntryName / Fields 计数 |
| `kingdee_add_entry_entity({ extensionFid, entityKey, entryName, defaultRows? })` | 新建 1:N 子表：CREATE TABLE + tracker 行（FTABLEID ≥ 900000）+ OBJECTTYPEREF 行（外键引用父 PK）+ 父扩展 FKERNELXML 加 `<EntryEntity>` 节点 + backup |
| `kingdee_add_field` 扩 `entityKey` 参数 | 默认空 = head；非空 = 加到指定 entry 的 Fields |

**关键风险**：
- FTABLEID 全局唯一性（需查 `MAX(FTABLEID)` 在 `T_META_TRACKERBILLTABLE`，避开 BOS Designer 内部分配区 100000-500000，从 900000+ 起选）
- 父扩展 FKERNELXML 的 `<EntryEntity>` 节点位置（在 head Fields 之后，其他 entry 之间按 Seq 排序）
- 删除 entry 时不仅是 XML 改动 — SQL DROP TABLE 物理表 + 还原 tracker / refs

**测试**：3 个新单测文件（`bos-entity.test.ts` / `bos-add-entry.test.ts` / `bos-add-field-with-entity.test.ts`）覆盖建表 SQL + XML 形状 + tracker 选号 + backup 路径 + 父扩展不被破坏

### 5.12.3 业务规则（route C — validate-and-retry）（依赖 5.12.1 完成，估 9-13 天）

**Tier B 侦察需求**：**高** — 1-2 天专门做：
- 完整 IronPython 子集（BOS 实际允许哪些语法 / 哪些 .NET 类）
- 全部 FuncDefine（不仅是 18 个明显的，还有日期 / 时间 / 数学 / 字符串 / 等更多）
- DependencyRules 触发模型（DataChanged / BeforeF7Select / AfterDelEntryRow 等事件名 + 参数）
- 一个真实业务规则 XML 节点形态（找客户 dev 环境扒一条）

**P0 工具**：

| 工具 | 范围 |
|---|---|
| `kingdee_add_business_rule({ extensionFid, target, when, action })` | 加业务规则。`action` 是 LLM 直出 IronPython；工具内部跑 validator + retry 1 次失败则返回详细错误给 LLM |
| `kingdee_list_business_rules(extensionFid)` | 列已有规则 |
| `kingdee_delete_business_rule(extensionFid, ruleId)` | 删规则 |

**Validator 模块**（`bos-business-rule-validator.ts` 新建）：

```typescript
function validateBusinessRule(action: string, schema: BillSchema): ValidationResult {
  // 1. AST 解析 (用 python-ast 库 or 简单递归下降)
  // 2. 检查所有函数调用对照 FuncDefine 白名单
  // 3. 检查所有字段引用 (this.F字段 / GetFieldValue('F字段')) 在 schema 里存在
  // 4. 返回 { ok: true } 或 { ok: false, errors: [...] }
}
```

**Retry loop**（`agent/loop.ts` 内 `kingdee_add_business_rule` 的 tool wrapper 层级）：
- 1 次重试机会
- LLM 失败后给的 error message 必须**精确**到行号 + 出错原因 + 建议（"`GetCurrentTime()` 不存在，可能是 `GetTime()` 或 `GetDate()`"）
- 2 次失败硬错给用户

**测试**：5+ 单测覆盖 happy path + 函数白名单错配 + 字段不存在 + IronPython 语法错 + retry 成功

### 5.12.4 转换规则（只读）（独立，估 2-3 天）

**Tier B 侦察需求**：中 — 半天扒一个真实 ConvertRule XML 节点形态

**P0 工具**：

| 工具 | 范围 |
|---|---|
| `kingdee_list_convert_rules(billObjectKey)` | 列某单据已有的下推规则（"销售订单 → 发货 / 销售订单 → 收款"等）|
| `kingdee_describe_convert_rule(ruleId)` | 详细解释一条规则：源单据 / 目标单据 / 字段映射 / 过滤条件 |

**不做**：创建 / 修改转换规则（`kingdee_add_convert_rule` 留 v0.2）。

**理由**：让 agent 至少能"告诉客户现有下推链路"，对实施顾问已有价值。创建留以后。

### 5.12.5 反写规则（独立，估 2-3 天）

**Tier B 侦察需求**：中 — 半天扒 WriteBackRuleElement 实际 XML

**P0 工具**：

| 工具 | 范围 |
|---|---|
| `kingdee_add_write_back_rule({ extensionFid, sourceField, targetBill, targetField, action })` | 加反写规则（如 "发货单审核 → 反写销售订单已发货数量"）|
| `kingdee_list_write_back_rules(billObjectKey)` | 列已有反写规则 |
| `kingdee_delete_write_back_rule(ruleId)` | 删规则 |

`action` 可选 `'sum' / 'minus' / 'set' / 'increment'` 等（实证后定）。

### 5.12.6 操作 / 按钮（独立，估 3-4 天）

**Tier B 侦察需求**：中 — 1 天补 FormOperation 完整属性 + plugin 绑定模型

**P0 工具**：

| 工具 | 范围 |
|---|---|
| `kingdee_add_operation({ extensionFid, key, caption, icon?, plugin?, visibility? })` | 加自定义按钮（key/中文名/图标/绑定的 Python 插件 / 可见性） |
| `kingdee_list_operations(extensionFid)` | 列已有操作 |

## 决策记录（重要的"为什么这样做"）

1. **6 项全做（A）而不是 MVP**：实施顾问最常做的 6 类需求都包含，alpha 就能撑客户实测
2. **业务规则走 validate-and-retry（C）而不是直白 a 或 DSL b**：a 太脆 / b 阉割 LLM 能力；C 利用已实证的 18 FuncDefine 白名单做 typed retry，是 v0.1 真差异化卖点
3. **转换规则只做读不做写**：10 个 ConvertPolicy 子类太复杂，单独占 7-10 天，独占工程量大风险高 → 留 v0.2
4. **基础资料属性单独工具**：BasePropertyField 必须有 sourceField + srcDisplayFieldName 强约束 → 独立 `kingdee_add_base_property_field` 比 `add_field` 一个超级参数列表清晰
5. **Tier B 嵌入而非前置**：不等所有侦察完才开发——业务规则 / 实体的高风险项侦察清楚，其他可在写 sub-plan 时按需补
