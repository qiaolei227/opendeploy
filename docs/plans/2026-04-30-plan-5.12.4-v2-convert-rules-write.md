## SaveRulesV9 wire format（实证总结）

```
ap0 = {
  "__rules__": [<rule1Str>, <rule2Str>, ...],   // JSON 字符串数组
  "__oldIds__": "[\"id1\",\"id2\"]",            // 旧规则 ID 集合(JSON 字符串)
  "__isv__": "{...}"                            // 顶层 ISV(JSON 字符串)
}

each ruleStr = {
  "2052": "",                                    // zh-CN 多语言副本(预留)
  "1033": ""(option),                            // en-US
  "3076": ""(option),                            // zh-HK
  "__source__": "<?xml ...?><ConvertRuleMetaData><Rule>...</Rule></ConvertRuleMetaData>",
  "__paras__": "<JSON: Id, OldId, ModelTypeId, BaseObjectId, Version, MainVersion,
                 PackageId, HasExtends, RunTime, ISV: {Id, Name, ISVSignal, PackageSignal,
                 DevCode}, InheritPath, IsInheritElement, FirstNonExtendObjectID,
                 ModelTypeSubId, Name>"
}
```

### 操作类型 → wire format 模式

| 操作 | `__rules__` | `__oldIds__` | rule.paras.OldId | rule.paras.Id |
|---|---|---|---|---|
| **创建扩展** | [origin, newExt] | [origin.Id] | null | new-guid |
| **修改扩展** | [origin, modifiedExt] | [origin.Id, ext.Id] | ext.Id（标识改的是哪条）| ext.Id |
| **删除扩展** | [origin] | [origin.Id, deletedExt.Id] | — | — |

**核心**：服务端 diff 应用 — 比对 oldIds vs rules.Id，差集 = 被删；rules 中 OldId=null = 新建；OldId=非空 = 修改。

### 扩展规则的 paras 关键字段（实证 #0163 rule[1]）

```json
{
  "Id": "<新 32-hex compact GUID>",
  "OldId": null,                           // 新建必为 null
  "ModelTypeId": 790,                       // 转换规则的 ModelType
  "BaseObjectId": "",
  "DevType": 0,
  "Version": null,                          // 服务端填
  "MainVersion": null,                      // 服务端填
  "PackageId": null,                        // 服务端填
  "HasExtends": false,                      // 扩展自身不带扩展
  "RunTime": false,
  "InheritPath": null,                      // 服务端填(基于 oldIds 推断)
  "IsInheritElement": false,                // wire format 用 false,设计时 view 推断为 true
  "FirstNonExtendObjectID": null,
  "ModelTypeSubId": 0,
  "ISV": {
    "Id": "IBHC-LMFG-QIMZ-LHQA-VFBK",      // 项目级 devCode 对应的 ISV.Id
    "Name": "UNW",                          // = devCode
    "ISVSignal": "Kingdee",
    "PackageSignal": "",
    "DevCode": "UNW"
  },
  "Name": "[{\"Key\":2052,\"Value\":\"转换规则\"}]"  // 中文名(用户传)
}
```

**关键**：`ISV.Id` 不是项目存的 devCode 字符串，是**服务端注册的 ISV 实体的 GUID**（实证值 `IBHC-LMFG-QIMZ-LHQA-VFBK`）。需要：
- 项目设置加 `bos.isvId` 字段（实施顾问从 BOS Designer 应用管理对话框抄过来）
- 或调 RPC 反查 ISV.Id（待找端点）

### 扩展规则的 XML 内容（实证 #0163 rule[1]）

XML 52KB（vs 原厂 101KB），动作属性只有 `action="setnull"`。**没有 `action="add"`**（新元素 = 不带 action）。**没有 `action="edit"`**（修改 = 完整重传该元素）。

XML 包含 `<LinkEntityPolicy>` / `<BillTypeMapPolicy>` / `<DefaultConvertPolicy>` / 等 Policy 顶层节点，子内容根据扩展实际改动量决定。

### origin 规则的 wire format 必须保持原状

每次写都要把 origin 规则**原封不动**包在 `__rules__[0]` 里（实证：#0163 origin XML 101140 字符 = #0153 origin XML 101140 字符 = #0081 origin XML 101113 字符，差异是 `MainVersion` 字段少 27 字符）。

意味着我们的写工具必须：
1. 调 `GetConvertRule(originId)` 拉 origin 的 runtime view（240KB JSON）
2. 把它转回 DCXML（reverse summarize → emit）
3. 跟新扩展一起 SaveRulesV9

或者更简单：我们的工具**只支持已存在扩展的修改**，第一次创建扩展时 BOS Designer 已经帮我们做了 origin 的全量 emit。

实际策略：
- **创建扩展时**：只构造扩展自己的 minimum-viable XML + paras（Source/TargetFormId + 1 个空 LinkEntity 等服务端要求的最小元素），origin 那侧从最近一次 `GetConvertRule(originId)` 的响应缓存。
- **修改扩展时**：拉当前 ext.runtime view，反向 emit DCXML，patch 想改的 Policy/FieldMap，重传 origin + modifiedExt。
- **复用 origin XML**：第一次需要时实证抓一份"BOS Designer 加扩展但不改 origin 任何东西"的 SaveRulesV9，存成 baseline，后续创建直接复用。

## 风险与缓解

1. **ISV.Id 来源未确定** —— 实证拿到的是 GUID `IBHC-LMFG-QIMZ-LHQA-VFBK`，不知是哪个 ISV-Reg 端点返回的
   - 缓解：项目设置加 `bos.isvId` 字段，让顾问从 BOS Designer 应用管理对话框手动抄过来；后续找到注册 RPC 再自动化
2. **Origin 规则的 XML 必须重传完整** —— 240KB JSON → 100KB DCXML 的反向序列化复杂
   - 缓解：直接缓存 BOS Designer 抓到的 origin XML 作为 baseline，每次 SaveRulesV9 复用；origin 内容长期不变
3. **写错了规则可能影响下推流** —— 客户业务受影响
   - 缓解：每次写之前 GetConvertRule 拉一份当前 ext + 落到 `~/.opendeploy/projects/<id>/convert-rule-backups/<ts>_<extId>.json`；agent 暴露 restore 工具
4. **Plan 5.12.5 反写 / 5.12.6 操作可能也走 SaveRulesV9 类似路径** —— 重复造轮子
   - 缓解：Task 1 的 paras builder + envelope wrapper 抽象成通用模块，5.12.5 / 5.12.6 复用
